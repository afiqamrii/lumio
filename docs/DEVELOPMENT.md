# Development

## Stack and SDK

Flutter 3.38.6 stable / Dart 3.10.7 form the verified baseline. Riverpod supplies
the provider scope and router lifetime; go_router supplies declarative routing.
Flutter gen-l10n, flutter_localizations and intl supply English and Bahasa Melayu.

Resolved runtime packages: flutter_riverpod 3.3.2, go_router 17.5.0 intl 0.20.2 and flutter_svg 2.3.0; flutter_lints 6.0.0 is a development dependency. Pub selected stable versions compatible with this SDK. Latest-package compatibility can be checked on [pub.dev](https://pub.dev/) before a deliberate SDK upgrade.
Bundled brand fonts work offline. The lockfile belongs in version control.

Keep dependencies compatible with the installed SDK. Do not upgrade the shared
Flutter SDK implicitly. Phase 3 adds Drift/SQLite local persistence. Flame, Supabase and cloud integration remain later-phase choices. See PROFILES.md for SDK-compatible package pins.

## Run

From the repository root (`lumio-1`):

```sh
flutter doctor -v
flutter pub get
dart run build_runner build
# Windows x64 only, before tests: ./tool/prepare-test-sqlite.ps1
flutter devices
flutter run -d <device-id>
```

On Windows, Android can use a connected device or existing emulator:

```sh
flutter emulators
flutter emulators --launch <emulator-id>
flutter run -d <android-device-id>
```

For a development browser session (not part of the mobile acceptance gates):

```sh
flutter run -d chrome --no-web-resources-cdn
```

On macOS, run the same app on an iOS simulator. Physical iOS devices need an
Apple development team configured locally in Xcode. Windows cannot compile iOS.

## Public environment configuration

`AppConfig` accepts `development` (default), `staging`, or `production`.
Unknown names fail at startup so typos cannot silently select another environment.

```sh
flutter run --dart-define=LUMIO_ENV=staging
flutter run --dart-define-from-file=config/environment.example.json
```

For local customization, copy the example to `config/environment.local.json`.
Non-example JSON in config/, .env files, signing keys and service-account files
are ignored. The example includes no keys or backend URLs. Never commit
credentials; review staged changes before any future commit.

Dart defines and bundled config are extractable from the installed app. They
cannot protect secrets. A future backend phase may add explicitly public
Supabase project URLs and publishable client keys through this boundary, with
RLS and policies reviewed in that phase. Service-role keys, database passwords
and external-service secrets stay on the server or approved secret storage.
Do not add backend SDKs or network initialization in Phases 0–1.

## Localisation and accessibility

Device locale selects English or Bahasa Melayu; unsupported locales fall back
to English. Add future strings to both ARB files. Arabic font fallback is bundled,
but Arabic is not advertised as a supported UI locale yet. A future Arabic ARB,
Flutter's localisation delegates and directional layout permit RTL without a
routing or global-layout rewrite. Arabic translations, shaping and diacritics
need dedicated review.

Use directional padding/alignment, semantic labels, text-scalable layouts and
minimum 56 logical-pixel child controls. Do not cap system text scaling.
Use LumioMotion.reduced(context) and LumioMotion.duration(context, token) for transitions.
The design system uses subtle native transitions and no sound; all information is available with sound
disabled. Do not replace visible feedback with sound-only feedback.

## Phase policy

Each phase must be completed and tested before the next begins. Each phase
needs written acceptance criteria and recorded validation. Static analysis and
tests must pass before moving forward. Record significant architecture changes
in docs/ARCHITECTURE.md or an architecture decision record. Keep future features
out of earlier phases, including placeholder business state with no actual need.

Phase 0 acceptance:
- runnable Android/iOS scaffold and minimal branded landing route;
- Riverpod scope, disposable go_router, English/BM generation;
- exact brand colors and offline licensed fonts;
- public environment strategy, ignored sensitive files, debug logging boundary;
- responsive phone/tablet layout and meaningful tests;
- formatting, pub get, analysis, tests, Android debug build where possible;
- startup check and asset-preservation/dependency/secret review.

Phases 1–6 are implemented. See DESIGN_SYSTEM.md, NAVIGATION.md, PROFILES.md,
CHILD_EXPERIENCE.md, PROGRESSION.md, LEARNING_ENGINE.md and the verification
histories. Playable learning games remain intentionally absent.

## Preview and local-data testing

Debug non-production Parent Settings includes **Learning Content Browser**.
Use it to inspect the six local subject catalogs, skill prerequisites, typed
items, deterministic seeded sessions, and catalog validation. The route is not
registered in release/profile builds or production configuration. Run
`flutter test test/learning` after changing catalog or learning-domain code.

Normal launches use persisted setup and child selection. Both preview flags default false. Explicit LUMIO_NAVIGATION_PREVIEW=true opens the debug chooser; LUMIO_DESIGN_PREVIEW=true opens the gallery. Release/profile/production reject both. Debug non-production Parent Settings separates Reset Progression Data from the confirmed Reset Lumio Local Data action.

Run flutter pub get, flutter gen-l10n, dart run build_runner build, formatting, flutter analyze, flutter test and flutter build apk --debug. Windows x64 tests use ./tool/prepare-test-sqlite.ps1 once per fresh .dart_tool; Linux CI uses full system SQLite. The current Windows system SQLite omits foreign keys.

Child fields are nicknames, a 5–9 placement hint, predefined symbol avatar and English/BM language. No child email, DOB, photos, location, school or account credentials are collected. Profiles stay local to Lumio; clearing app data/uninstalling removes them. See PROFILES.md for storage/OS backup limits and future repository integration.
